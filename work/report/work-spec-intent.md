# 两份规格背后的两种意图

写这份报告是因为照领域规格落不了地，于是另起炉灶写了一份 work 文档语法。落不了地这件事本身不是结论——真正的差别在两份东西对「需求」的理解不同：一份要**管得清**，一份要**做得成**。全文三段：先各自说清要什么，再定性看两边把同一件事长成什么样，最后按可数的口径逐项比。

## 一、两种理解：要管得清，还是要做得成

领域规格面对的需求是「多个平台各自实现，怎么保证口径一致」。所以它要先立概念：谁的地盘、什么东西、经过哪些环节、每一步谁有权放行。这些问题答清了，两个平台做的系统才能互相认、审计才能对得上。它承认的边界也很清楚：形式化建模到此为止，具体实现不在讨论范围。**它的意图是让工作可被管理、可被追溯、可被替换而不失真。**

work 文档语法面对的需求完全不同：一个人想让机器替他把同一件事做上几十遍，还得每次结果一样。所以它要先立能跑的东西：靠什么做、谁动手、凭什么算过、换实现要不要改定义。**它的意图是让一件事能被重复做出来，且做得对不对能当场判。**

两种意图不冲突，但各自会把同样的词填成不同的东西。「工作」在规格里是治理对象——有归属、有凭证、有账本；在语法里是工序——有输入、有手段、有判定。这个分野决定了后面全部差异。

## 二、定性对比：同一件事，两种长法

拿一件真事走两边：从相册导出素材、转成通用格式、收拾进两个目录。

在规格的理解里，这件事要先有工作区（归谁）、再有一条工作流声明走过哪几站、然后开一张任务账本逐站记账，最后交出一件有名字、有验收标准的产物。它关心的是**这一路的责任与凭证是否留痕**：谁开的、走过哪站、谁放的行，将来能不能查到。

在语法的理解里，这件事只有一个文件：四个输入、五个步骤、两条能力、七条判定。它关心的是**这一路能不能重跑**：跑到一半断了能不能接着跑，换一个实现要不要改文件，判定成立不成立机器能不能自己说。

三种分野由此显出来。

**账的方向不同。** 规格记的是「谁对什么负责」，一条记录是给事后追查用的证词；语法记的是「这一步过没过」，一条判定是给当下推进用的开关。前者向后看，后者向前走。

**成事的标准不同。** 规格的完成是「交出一件东西并被验收」；语法的完成是「判定全部成立」。前者要求成果可命名、可封存，后者只要求状态对。所以收拾摊子这类活——导出、同步、转码、清理——在语法里天然有位置，在规格里必须被硬说成「产出某物」才装得进去。

**放行的方式不同。** 规格把「谁动手」和「谁放行」当成一件事回答，因为治理只认责任：谁签字谁负责；语法必须把两者分开，因为工序关心的是谁来做、以及做完凭什么算过——这两件事常常不是同一个人或同一台机器。

所以同一条流水，在一边是「一串可追溯的责任点」，在另一边是「一串可判定的动作」。这就是定性上的根本差别，也是照规格写不出可跑流程的原因。

## 三、定量对比：按可数的口径逐项比

统计口径先写明：取上面那件真事，把它在语法里写成一份 189 行的文档（其中声明块 57 行），逐项计数；再用规格的模型描述同一件事，按它自己规定的位置计数。两边的分母是同一件事。

| 维度 | 计数口径 | 领域规格 | work 语法 |
|---|---|---|---|
| 一站能落笔的位置 | 除自动派生外的字段数 | 2（站名、一句话交代） | 4 必填（做什么、靠什么做、谁做、谁判）+ 3 可选 |
| 可机器判定的判定条数 | 该事共有 7 条判定 | 0 / 7（判法下放给平台，规格自身不给形状） | 7 / 7 |
| 需要人兜底的步骤 | 无法机判、只能人看的步骤 | 5 / 5 | 1 / 5（只剩颜色确认） |
| 「谁动手」与「谁放行」 | 两个位置各有字段 | 合为一处 | 分为两处 |
| 改一处判定的代价 | 一次修改要新立几个对象 | 1 个新定义（旧定义留档、账本断开） | 0（同一文件改文本，不动账） |
| 换实现是否改定义 | 换命令或换实现 | 定义里没有做法位置，无可对照 | 0 处改动（只改能力实现） |
| 该事能否落位 | 能否在模型里表达 | 不能：必须有可验收产物，本案例没有 | 能：幂等过程即可 |
| 治理要素 | 工作区、凭证、账本、验收 | 全备 | 全无 |

读这张表要连着分母读，否则会误判成「新的全面赢」。前六行的分母是同一件事的七个判定与五个步骤：在「做得成、可机判、可迭代」这三项上，语法是 7/7、4/5 步可机判、改一处代价 0；规格在这三项上分别是 0/7、0/5、每改一处立一个新定义。可第七、八行反过来，分母是治理所要的四个要素，语法是 0/4——它没有归属、没有凭证、没有账本、没有验收。

所以这不是一场谁赢的比较：**规格擅长的是留痕，语法擅长的是落地。** 缺了治理，跑得再顺也留不下证据；缺了执行，管得再清也推不动一步。真正该做的不是二选一，而是承认两份东西各自回答一个问题——然后决定由谁承担哪一半。

## 边界与下一步

本报告只比意图与可见的落笔位置，不评价规格的接口与事件设计，也不定实现。

下一步不依赖任何人同意：先在一份真实文档里把「谁动手」与「谁放行」分开，这一步做完，规格哪一处必须动就自己露出来了；再用「发一条图文到两个平台」试交件的活与收拾摊子的活能不能用同一套写法装下——那件事既交件又要重跑，正好卡在两种意图的交界上。

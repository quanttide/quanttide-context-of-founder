# work 语法草案暴露的工作规格缺口

**为什么写这份报告**：领域规格框架完整，照它落细节却处处卡手。于是从零写了一份 work 文档语法（`work/specification/syntax.md`），用意不是另立标准，而是用「从零写一遍」逼出卡手的真因——哪些只是措辞，哪些是框架里本来就缺的位置。下面把过程写成一份可以据此拍板的清单。

## 结论：一站五件事，规格写成了三件

写一份 work 时，一站要填五件：做什么、靠什么做、谁做、谁判、算不算完。规格里的站是「站名 + 一句话 + 谁判」——五件写成三件。

缺的三件：

**靠什么做**没有位置。步骤只有一句 `description`，写这一步要干什么，没有地方写靠什么执行。照规格落成文件，「怎么跑」只能散在散文里，于是同一份流程两个人写得不一样、机器读不了、换实现也无从换起。

**谁做**没有位置，而且与规格另一处打架。执行者组几篇都说「每一步带一个 `executor`」「执行者内嵌于工作步骤」，可工作步骤的字段表只有 `id`、`name`、`description` 三枚，`executor` 实际只出现在判据里。这是规格自相矛盾，不是设计取舍。写的时候一撞就露：我有一站是「人确认颜色」，人做、机器判（人抽样看 HDR 有没有发灰，机器查有没有残留格式文件），一个 `executor` 装不下两问。

**判什么**只剩判定者。判据两个字段，`executor`（谁判）与 `description`（一句话），而 `rule` 判据的判法「由平台定义」——最要紧的那件事被一句话推给了平台。机器要判的东西不能是一句话。草案里那四种句式（`退出码为 0`、`<对象>: 无 <模式> 残留`、`<对象>: 只含 <模式>`、`<对象>: 数量与 <来源> 一致`）就是被这个缺位逼出来的：判据应当是「谓词 + 判定者」，规格只留了判定者。

## 两处后果，决定框架能不能落地

**不可变压在了身份上。** 定义一经工作任务引用即不可变，改站名、删步骤、调次序须另立工作流。靶子要死我认，但我一天之内把判据句式改了三遍——照字面每改一字就换一个身份，同一个 work 在账本里散成七八个「工作流」。要的是定义带版本、账本钉版本号：靶子仍死，定义仍活。

**只承认产出型过程。** 规格只给「产物有名字、有验收判据」这条路。可实际要跑的有一大半是操作型：导出、同步、转码、清理——跑完没有产物，只有目录状态变了，正确的做法是幂等重跑。这类恰恰最适合先做成 work（可机判、可重跑、可夹具），框架里却无处归类，于是永远停在纸面。

## 重组清单

1. **修规格自身的矛盾**：`executor` 要么写进步骤字段，要么改掉执行者组那句声称。验法：两处对读，是否指同一个位置。
2. **判据拆成谓词 + 判定者**。验法：机械、智能体、人三种判据各写一条，看谓词能否落到结构字段而不是散文。
3. **声明侧加「靠什么做」**。验法：同一份流程换一份实现（真实命令 / mock），流程定义是否一字不改。
4. **定义带版本、账本钉版本**。验法：改一次判据，旧账仍对得上，新账指新版本。
5. **承认操作型过程**。验法：拿「导出并规范化一批素材」当例子，看它在规格里能否落位。
6. **本体与平台实现分篇**：现在每篇都带领域事件与 API 端点，文件层抄不动。验法：只读本体篇的人，能否不看端点就说出这个概念有几个字段、谁可改。

## 草案自己的两笔账

执行者要按规格三分（规则引擎 / 智能体 / 人），草案混成了「系统 / 人」，会让该智能体判断的步骤被当机械校验跑过去。版本语义要改成「另立」，否则与不可变纪律打架。另外草案在步骤外多了七个区，规格是封闭字段集，将来若进平台资源需先登记扩展位。

## 边界与怎么核

只对照概念与字段，不评价规格的 API 与事件设计，不决定执行器怎么写。

可核之处：草案 `work/specification/syntax.md`（约 200 行，含一个 `yaml work` 块）；规格 `quanttide-work` 的 `docs/specification`（24 篇 624 行）；本报告引用的条款集中在工作步骤（字段表三枚与不可变约束）、工作流（判据两字段与 `executor` 取值）、产物（规格是一组验收判据）。

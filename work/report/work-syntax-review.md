# work 语法草案与工作规格的对照

**一句话结论**：两者不是替代关系，草案是工作规格「过程组」的下位实现。有两处必须改（执行者要三分、版本号与不可变纪律冲突），有三处要谈（扩展字段与封闭字段集、判据句式归属、输入与能力层要不要进规格）。

对照对象：本仓 `work/specification/syntax.md`（200 行）与工作领域的规格仓（`quanttide-work` 的 `docs/specification`，24 篇共 624 行，其中过程组 5 篇 287 行、执行者组 4 篇 42 行）。

## 一、两边各是什么

工作规格是领域级规范：给知识工作做形式化建模，定概念、领域事件与 API，明确各平台「必须」遵循什么。它的四个零件是场所（工作台 / 工作区）、工件（材料 / 产物）、过程（工作流 / 工作步骤 / 工作任务 / 工作记录）、执行者（人类 / 智能体 / 规则引擎）。

本草案是文件级规范：一份 work 文档怎么写才既让人能照做、又能被执行器读懂。

所以层级不同：规格回答「这个概念是什么、有哪些字段、谁能改」，草案回答「一个 work 文档里的块长什么样」。

| 概念 | 工作规格 | 本草案 |
|---|---|---|
| 过程定义 | 工作流 `Workflow`：REST 资源，凭证按「工作区 id + 名」派生，被引用后不可变 | work 文件的 `yaml work` 块 |
| 一站 | 工作步骤 `WorkStep`：`id` + `name` + `description` 三枚 | 步骤：`id`、`做`、`参数`、`执行者`、`判据`、`幂等`、`产物` |
| 怎么算完 | 判据挂在步骤上，两个字段：`executor`（谁判）+ `description`（一句话） | 判据四种固定句式，可机判 |
| 谁做谁判 | 人类 `human` / 智能体 `agent` / 规则引擎 `rule` | `系统` / `人` |
| 执行事实 | 工作任务 `WorkTask` + 工作记录 `WorkRecord`，只增不改，进度靠推导 | 无（草案只管定义，不管跑） |
| 场所 | 工作台 / 工作区，一层对多 | 无（隐含是一个目录） |
| 工件 | 材料（无规格）/ 产物（有名字与验收规格） | 无 |

## 二、对得上的地方

1. **判据挂在步骤上**，不是挂在流程上——两边一致。
2. **不设状态字段**。规格明写「进度与完结只许推导，不许落字段」，草案的全部步骤也没有 `状态` 字段，只靠判据判定。
3. **先声明后执行**。规格的「步骤先声明后执行，声明了才有资格出现在流水里」与草案「块是声明、散文是说明」是同一个意思。
4. **步骤要能被指认**。规格靠 `name` 对账、`id` 跨区；草案的 `id` 也是本篇唯一。方向一致，只是分工不同（见下）。

## 三、必须改的两处

**一，执行者要分三类。** 规格分人类、智能体、规则引擎；草案只写 `系统` 与 `人`，把智能体与规则引擎混成一个。这两者判定方式根本不同：规则引擎机械比对（`rule` 的判法由平台定），智能体要照判准审查（`agent` 只写 `description`）。草案现在的写法会让一个需要智能体判断的步骤被当成机械校验跑过去。

改法：`执行者` 取值改为 `规则引擎` / `智能体` / `人`；判据按执行者分别要求——规则引擎给可机判句式，智能体与人给一句话判准。

**二，`版本` 字段与不可变纪律冲突。** 规格说：定义一经工作任务引用即不可变，改站名、删步骤、调次序须另立新工作流，旧定义原样保留。草案的 `版本` 写的是「改步骤或判据加 1」，等于允许原地演进，与这条纪律相反。

改法二选一，我倾向前者：

1. 把 `版本` 改成「另立」语义：改步骤就是新版本、旧版原样留档，块内 `版本` 只是给同一 work 的不同留档编号；
2. 明确草案只约束「尚未被引用的定义」，一旦有账即冻结，冻结后修改即视为不合规。

## 四、要谈的三处

**一，封闭字段集与扩展字段。** 规格的约束是「字段取值之外一律拒绝：不认识的字段、缺必填字段，取值不在枚举内，均视为不合语法」。草案在步骤之外还加了 `输入`、`前置`、`校验`、`偏差`、`不做`、`能力`、`幂等` 七个区。若这些将来要进平台资源，必须先在规格里登记扩展位；若不进，就要明写它们是「文件载体专用，不入资源」——否则两边各自解释，验收时必打架。

**二，四种判据句式归谁。** 规格说 `rule` 判据的「判法由平台定义」，草案的四种句式（`退出码为 0`、`<对象>: 无 <模式> 残留`、`<对象>: 只含 <模式>`、`<对象>: 数量与 <来源> 一致`）正好可以当那一份平台判法。建议作为附则援引进规格，而不是规格里写「平台定」、文件里写四种，两处各说一套。

**三，要不要把「能力」概念写进规格。** 这是草案最有价值、规格最空白的一块。规格的 `WorkStep` 只有一句 `description`——照它执行，「怎么跑」全靠散文，机器跑不了；草案把「做」与「怎么做」分开：块里只写能力名与参数，命令与脚本留在散文与执行器的能力实现里，于是 mock 只换实现、不换流程，整条流程可以在夹具上跑通。

换来的代价是引入了一层规格里没有的东西。这层要不要升格进规格，取决于工作云是否打算在平台侧跑 work——不跑，就留在文件规范里；要跑，就得先在规格里给能力一个位置。

## 五、本报告的边界

- 只对照概念与字段，不评价规格的 API 与领域事件设计
- 不涉及场所组与工件组（草案里没有对应物，无可对比）
- 不决定执行器怎么写、work 语法是否升回正式规格仓

## 六、下一步（按成本从低到高）

1. 改草案两处必改项：执行者三分、版本语义（预估半天）
2. 拿二例验证语法够不够用：Live Photo 归位这类分支步骤，以及一条需要智能体审查的步骤（半天）
3. 把四种判据句式作为提案提给工作规格方，而不是我们在本仓另立一套（一天）
4. 执行器落地后，再谈输入与能力层是否升为规格条款

## 怎么核

- 草案：本仓 `work/specification/syntax.md`，200 行，含一个 `yaml work` 块
- 工作规格：`quanttide-work` 仓的 `docs/specification`，24 篇 624 行；关键条款在工作步骤（三枚字段与不可变纪律）、工作流（判据两字段与 `executor` 取值）、工作任务（进度只许推导）、工作记录（只增不改）
- 本文引用的条款均可按上述两处逐条对照

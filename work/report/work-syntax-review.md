# work 语法草案与工作规格的对照

## 为什么写这份报告

领域规格（`quanttide-work` 的 `docs/specification`）框架完整，但照着它落细节时处处卡手。于是另起炉灶写了一份从零开始的 work 文档语法（本仓 `work/specification/syntax.md`），用意不是另立一套标准，而是**用「从零写一遍」逼出卡手的真因**：哪些只是措辞不顺手，哪些是框架里本来就缺的位置。

这份报告就是那份清单，附对照证据。

**结论先行三条**：

一，草案不是规格的竞争者，是它的下位实现——规格回答「这个概念是什么、有哪些字段、谁能改」，草案回答「一份 work 文档里的块长什么样」。

二，卡手的真因是**规格把一站写成了三件事，而一站实际是五件事**。规格里一站是「站名 + 一句话 + 谁判」；实际写 work 时一站要写清五件：做什么、靠什么做、谁做、谁判、算不算完。五件里有两件在规格里没有位置，一件与规格自身的另一处说法矛盾。

三，其中「谁做」的缺位是**规格自相矛盾**，不是设计取舍，可以立刻修；其余是结构缺位，要重组。

对照规模：规格 24 篇共 624 行，其中过程组 5 篇 287 行、执行者组 4 篇 42 行；草案 200 行。

## 一、两边各是什么

先说两个词，后面一直用：

- **声明侧 / 事实侧**：规格把过程分两半——声明侧说打算（工作流、工作步骤），事实侧说交代（工作任务、工作记录）。声明是「要这么走」，事实是「这么走过了」。
- **产出型 / 操作型过程**：产出型跑完交出一件产物，产物有名字、有验收规格；操作型跑完没有产物，只有环境状态变了（目录里多了一批文件、格式统一了），且正确的做法是幂等，重复跑一遍结果一样。

规格的四组零件是场所（工作台 / 工作区）、工件（材料 / 产物）、过程（工作流 / 工作步骤 / 工作任务 / 工作记录）、执行者（人类 / 智能体 / 规则引擎）。

草案是一份文件格式：一个 work 文档里嵌一段 `yaml work` 块，块管步骤、判据、偏差；散文管真正要敲的命令与取舍理由。

同一个概念在两边的落点：

| 概念 | 工作规格 | 本草案 |
|---|---|---|
| 过程定义 | 工作流：REST 资源，凭证按「工作区 id + 名」派生，被引用后不可变 | work 文件里的 `yaml work` 块 |
| 一站 | 工作步骤：`id`、`name`、`description` | 步骤：`id`、`做`、`参数`、`执行者`、`判据`、`幂等`、`产物` |
| 怎么算完 | 判据挂在步骤上，两字段 `executor` + `description` | 四种固定句式，机器可判 |
| 谁做谁判 | 一个 `executor` 取 `human` / `agent` / `rule` | `执行者: 系统 \| 人` + 判据句式 |
| 执行事实 | 工作任务 + 工作记录，只增不改，进度靠推导 | 无（草案只管定义，不管跑） |
| 场所 | 工作台 / 工作区，一层对多 | 无（隐含是一个目录） |
| 工件 | 材料无规格；产物有名字与验收规格 | 无（草案只承认跑完的结果，不承认产物） |

## 二、一站五件事，规格缺了哪几件

把写一份 work 时真正要填的槽位列出来，对着规格看：

**做什么 —— 有。** 步骤的 `description` 就是这一句：到了这站干什么。规格还专门定了方向：写意图不写结局（「做安全评审」可以，「安全评审已通过」不可以，结局只许出现在流水里）。这条很好，草案照抄。

**算不算完 —— 只有半个。** 规格的判据是两个字段：`executor`（谁判）与 `description`（一句话）。谁判有了，可「判什么」只剩一句话，而且规格明写 `rule` 判据的判法「由平台定义」——最要紧的那件事被一句话推给了平台。机器要判的东西不能是一句话。

草案里那四种句式就是被这个缺位逼出来的：`退出码为 0`、`<对象>: 无 <模式> 残留`、`<对象>: 只含 <模式>`、`<对象>: 数量与 <来源> 一致`。它们补的不是风格，是判据缺失的那一半——**判据应当是「谓词 + 判定者」两件，规格只留了判定者**。

**谁判 —— 有。** `executor` 在判据里，取值 `rule` / `agent` / `human`。

**谁做 —— 没有，而且与规格另一处打架。** 执行者组的几篇都说「工作流里每一步带一个 `executor`」「执行者内嵌于工作步骤」；但工作步骤的字段表只有 `id`、`name`、`description` 三枚，没有 `executor`——`executor` 实际只出现在判据里。

这不是修辞冲突，一写就撞：我写「人确认颜色」那站，人做、机器判（人抽样看 HDR 有没有发灰，机器查有没有残留格式文件），一个 `executor` 装不下两问。规格说执行者回答「由谁做、由谁判」，可它只给了「谁判」一个位置。

**靠什么做 —— 没有。** 步骤没有位置写「这站靠什么执行」。照规格落成文件，「怎么跑」只能散在散文里，结果必然不可测：同一份流程两个人写得不一样，机器读不了，换实现也无从换起。草案加的那层能力（块里只写能力名与参数，命令与脚本留在散文与执行器的实现里）不是花样，是这个缺件。

所以规格的声明侧实际只有三样东西：站名、一句意图、一个判定者。**能执行的三件——怎么做、谁做、判什么——全部缺位**，难怪写起来处处卡手。

## 三、定义不许动，换来账本有死靶子，代价是定义不能迭代

规格的纪律：定义一经工作任务引用即不可变，改站名、删步骤、调次序，须另立新工作流，旧定义原样保留。动机我认——账本对账靠名字，名字一动流水对不上账，靶子必须死。

但代价写在细节里：我一天之内把判据句式改了三遍，这在文档层是常态。照规格的字面，每改一个字就得换一个工作流身份，旧定义原样留档，于是同一个 work 在账本里散成七八个「工作流」，谁是真的推进不出来了。

真正要的不是「不许动」，是**定义带版本、账本钉版本号**：靶子仍然死（账本钉住的是某一版），定义仍然活（新版本另立，旧版本可读）。规格现在把「不变」压在了整体身份上，压力用错了地方。

## 四、两类过程，只有一类有位置

规格只承认产出型过程：产物有名字、有验收规格（一组验收判据），产物凭它通过验收，验收后完成使命。这条链很清楚。

可实际跑的东西里，有一大半是操作型：导出、同步、转码、清理。它们跑完没有产物——只有目录里的状态变了，而且正确的做法是幂等，重复跑一遍结果一样。草案里那篇导出 iCloud 照片就是典型：跑完交出的是一个规整过的素材目录，不是一件可以命名、可以验收的产物。

规格里没有这类过程的位置。这不是小事：操作型过程恰恰最适合先做成 work（可机判、可重跑、可夹具），也最能验证能力层。框架把它们排除在外，剩下的都是重的产出型流程，于是永远停在纸面。

## 五、本体与平台实现捆在每一篇里

规格每篇都有同样的三节：领域属性（含字段、凭证、约束）、领域事件、API 端点。作为平台规范这样写没问题，但**文件层抄不动**：写一份 work 文档不需要知道事件类型与端点路径，一抄就得连它们一起抄，于是文件里塞进一堆与「怎么写这一份」无关的东西。

本体（这个词是什么、有哪些字段、谁能改）与平台实现（怎么暴露成 HTTP 资源、发什么事件）应当分篇。凡是「平台必须提供某个端点」的条款，与「这个概念有这几个字段」不是同一类约束，混在一篇里，读者分不清哪条是概念纪律、哪条是某一代实现的约定。

## 六、草案这边同样要认两笔账

对照是双向的，草案也有错：

**执行者必须三分。** 规格分人类、智能体、规则引擎；草案只写 `系统` 与 `人`，把智能体与规则引擎混成一个。这两者判法根本不同（规则引擎机械比对，智能体照判准审查），混着写会让本该智能体判断的步骤被当机械校验跑过去。改法：取值改为三类，判据按类分别要求——规则引擎给可机判句式，智能体与人给一句话判准。

**版本语义与不可变纪律冲突。** 草案的 `版本` 写「改步骤或判据加 1」，等于允许原地演进，与规格的不可变纪律相反。改法：把版本改成「另立」语义——改步骤就是新版本，旧版原样留档；或者明写草案只约束尚未被引用的定义。

另外，草案在步骤之外加了七个区（输入、前置、校验、偏差、不做、能力、幂等）。规格的约束是「字段取值之外一律拒绝」，这七区若将来要进平台资源，必须先在规格里登记扩展位；若不进，就要明写「文件载体专用，不入资源」。两边各自解释，验收时必打架。

## 七、重组清单

按「能不能马上办」排，每条一句理由、一句怎么验：

1. **先修规格自身的矛盾**：执行者组声称 `executor` 内嵌于步骤，工作步骤的字段表里没有它。要么把 `executor` 写进步骤字段，要么改掉那句声称。验法：两处对读，是否指同一个位置。
2. **判据拆成谓词 + 判定者**：判据现在两字段（`executor` + `description`），缺谓词。验法：拿三种判据（机械、智能体、人）各写一条，看谓词能不能落到结构字段而不是散文。
3. **声明侧加「靠什么做」**：步骤只有一句意图，没有执行方式。验法：同一份流程换一份实现（真实命令 / mock），流程定义是否一字不改。
4. **定义带版本、账本钉版本**：把「不可变」从整体身份挪到账本一侧。验法：改一次判据，账本里旧账仍对得上，新账指新版本。
5. **承认操作型过程**：产出型之外补一类无产物的幂等过程。验法：拿「导出并规范化一批素材」当例子，看它在规格里能否落位。
6. **本体与平台实现分篇**：验法：抽一个只读「本体篇」的人，能否不看端点就说出这个概念有几个字段、谁可改。

## 八、本报告的边界

- 只对照概念与字段，不评价规格的 API 与领域事件设计是否合理
- 不涉及场所组与工件组的内部设计（草案里没有对应物，只记缺口）
- 不决定执行器怎么写，也不决定 work 语法是否升回正式规格仓

# 产物

> 状态：草案。与同目录 `syntax.md` 配套：那份定义一件工作怎么写，这份定义跑完之后应当存在什么。

产物是一次工作跑完后**应当存在的状态**，写成可数的描述。它不是「交出去的文件」，而是「指定位置的指定内容」。

产物一直存在——导出素材跑完，图片目录里就是图片、视频目录里就是视频。问题是它没被写下来时属于隐式产物：判定只能散落在各个步骤里，产物换一次样子就要改好几处，重跑对不对也无从判断。本文档的作用是把隐式产物写成显式的。

## 定义四问

四项必填，缺任何一项，产物仍是隐式的。

| 项 | 回答什么 | 例 |
|---|---|---|
| 是什么 | 产物的类型 | 素材集合、报告、目录 |
| 在哪 | 位置，一个或多个路径模式 | `<素材目录>/images`、`<素材目录>/videos` |
| 什么格式 | 形态：扩展名、编码、命名规则 | 图片只留 `.jpg`，视频只留 `.mp4`，扩展名小写 |
| 多少 | 数量口径 | 与相册中同类型条数一致 |

四项都是可数的，不含「看起来对」这类判断。

## 可选字段

- **来源**：产物从哪来。可以是另一个产物的位置，也可以是某次能力调用的返回值（如相册条数）。有来源才能写数量口径。
- **幂等**：重跑一次结果是否必须逐字节相同。取值 `是` / `否`，缺省 `否`。取 `是` 的产物必须能验证重跑一致。
- **类别**：报告、日志、素材集之类的归类。只供人读与检索，不参与验收。

## 判据

判据挂在产物上，不挂在步骤上。句式沿用三句：

| 句式 | 语义 |
|---|---|
| `<位置>: 只含 <模式>` | 该位置下所有文件都匹配该模式 |
| `<位置>: 无 <模式> 残留` | 该位置下不存在匹配该模式的文件 |
| `<位置>: 数量与 <来源> 一致` | 该位置的文件数与来源的计数相等 |

幂等取 `是` 时，另加一条总判据：本次结果与上次结果逐字节相同。

判据全部成立，产物成立；任一条不成立，这次工作不算做完。

## 与步骤的分工

步骤只写「这一步靠什么做、谁做」，不写产物长什么样。产物定义独立成立，不依赖步骤。

这条分工的验法是本文档的核心判据：**把全部步骤删掉，只留产物定义与判据，仍能判断这件事做成没有。** 能，说明产物真的被定义了；不能，说明判定还挂在过程上。

## 示例

```yaml artifact
artifact: exported-material
标题: 导出后的素材
是什么: 素材集合

位置:
  - "{{输入.素材目录}}/images"
  - "{{输入.素材目录}}/videos"

格式:
  images: 仅 .jpg，扩展名小写
  videos: 仅 .mp4，扩展名小写

数量:
  images: 与 相册照片条数 一致
  videos: 与 相册视频条数 一致

来源: iCloud 相册
幂等: 是
类别: 素材集

判据:
  - "images: 只含 *.jpg"
  - "videos: 只含 *.mp4"
  - "images: 数量与 相册照片条数 一致"
  - "videos: 数量与 相册视频条数 一致"
```

对照示例可以看出：原来写在步骤上的那些「无 HEIC 残留」「无 MOV 残留」，本质是产物判据，写在这里比写在步骤上更好改——产物变样子只改这一处。

## 与工作领域规格的对应

工作领域规格同样要求产物有名字与一组验收判据，这一点与本文档一致。

两处不同：规格把产物当作**交付物**（验收后封存、可作为后续材料）；本文档把产物当作**状态描述**（指定位置的指定内容），因此不要求封存，只要求可判。规格未规定产物的位置与数量口径，本文档把「在哪」「多少」列入必填，因为不写这两项就无法判断做成没有。

## 自检

1. 四问齐全：是什么、在哪、什么格式、多少
2. 每条判据都落在位置、格式或数量上，可逐项比对，不含「看起来对」
3. 删掉全部步骤，只看产物定义与判据，仍能判断做成没有
4. 幂等声明与实际一致：写 `是` 就必须能验证重跑一致

## 不做什么

- 不定义产物怎么生成——那是步骤与能力的事
- 不定义谁验收——判定由谁做出，属执行者职责
- 不定义封存与归档规则

呃，我实际的工作流程就经常写公众号写着写着有灵感过之后，然后我又呃那个倒回头去那个把这个公众号上发的再往这个 GitHub 仓库整理，然后再整理官网。就感觉到嗯这样做事情更加频繁自由一点，但是给后期治理增加了很大的负担。但是如果呃直接发的话，又会感觉到呃，就是按照我们正常的工作流，很多时候发不出来，因为那个工作流的话是非常高度的 AI 主导，你说写不出来东西。

我们 AI 这个地方应该是规格还是章程？AI 建议是章程，因为这里主要会有一个合法性交流，所以需要通过章程给自己授权。

这个我打算放在创始人章程。这个章程首先约束和授权创始人本人。人机关系也包括在内。

这里主要的执行难点就是自媒体回流这一步。

嗯，主要的原因是因为我有时候会在手机上写了以后，直直接在公司的公众号上发布，然后呢我就需要那个思考把它放到哪个仓库的位置，然后再整理。这个工作需要一个比较复杂的判断，然后还需要在电脑上操作，所以就会比较重，这个也是流程的主要冲突点。

这个地方的重点不是改章程，还是要想办法升级这个工作流，就是现在要从章程中出来，然后觉得我们可能需要做一个案例。

这个流程有点过度复杂了，还要走飞书，飞书的接入门槛很高，就其实我多一步动作就可以了，就是我先在公众号上写。写了过之后，然后把原文复制粘贴放到一个待整理的仓库的位置，一般是放在 context 里面。然后再加一笔待办，记得第二天要处理就完事，或者说不加待办也会批量处理就完事，所以其实就加这一步就可以。

不是 context 的文件夹，而是呃 context 的仓库，这类仓库它本来就是工作集，就是我无论是做自媒体还是做其他的工作，都会往这个里面去收集，所以不需要额外的流程。就在 GitHub 这一步细化一下这个就可以了，就是我无论怎么干了过之后，收集都可以往这个里面去收集。

对，我从这一轮修改就发现了一个基本原则，就是“最小改动原则”：我只需要动一个步骤就可以改变了。所以这样的话，其实我是在编辑自己的规则，通过这种方式，就很好地把规则组装了起来。

对，所以给自己写章程这个活动，本质上也是在整理自己的习惯，就是把它建立成一个更加高效的流转方式。

对，在这个地方，比如自媒体就能用数据，它是从我们的“第二大脑”出来的，那么这种形式就不需要回流；如果是我们直接写的，就需要回流。这样的话，其实就建立了一个更加反脆弱、符合直觉的自媒体工作形式。

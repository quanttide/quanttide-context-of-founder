# 架构设计说明书 v1.1 评审

- **评审对象**：《架构设计说明书 v1.1》
- **日期**：2026-10-25
- **性质**：逐条理解确认与开放问题，供系统契约与路线图对齐

---

收到。这份 v1.1 修订非常扎实，几个关键改动精准地堵住了上一版遗留的缝隙。我逐条确认我的理解：


——

对 v1.1 修订的理解确认

1. 世界状态与想定初始化（§2.2）

核心变化：L2 从“一组结算函数”明确为“一份可变的世界状态 + 一组在其上运行的结算函数”。

我的理解：

• world 模块是 L2 的心脏，持有所有动态数据

• new_game(scenario) 是唯一的写入入口——这意味着想定加载完成后，世界状态只能通过结算相位按规则改写，没有任何“后台偷偷改数据”的途径

• 地图/地形数据归属 L2 是正确的：它们是结算的依据，不是通用基础设施。如果将来要做编辑器，那也是 L2 的工具，不改变归属

确认一个问题：world.apply(result) 这个接口——result 是 movement/combat/supply 结算后的增量变更，对吧？也就是说，结算函数不直接修改 world，而是返回一个“补丁”，由 apply 负责落账。这样 world 的变更历史可以被完整追踪。


——

2. 关卡与登记哨户主（§3.2）

核心变化：关卡和登记哨不再是独立模块，而是 loop 的两个横切职责。

我的理解：

• 关卡 = 校验步骤 + 类型翻译步骤（Event → Report），发生在每次数据交接时

• 登记哨 = 五卷案卷的写入，发生在相位之间

• 两者都集中在 loop 里，不分散到各层

这个设计的好处：

• “先档后行”有了唯一的实现点，不需要靠各层自觉

• 审计时只需要看 loop 的代码，就知道所有数据在何时被记录

• 如果要加新的日志或校验，只改一处

确认：Event → Report 的翻译发生在关卡内，这意味着 fog 模块收到的已经是 Report 类型，它从来没见过 Event。这个隔离是在编译期完成的——L3 的代码根本 import 不了 Event 类型。


——

3. 接口签名修正（§2.3）

核心变化：fog/judge/decide/staff 的接口签名改为显式传入 turn 和 rng_stream，不再依赖 clock 和 rng 的全局状态。

我的理解：

• 这是“纯函数纪律”的具体落实

• 一个纯函数不应该在内部调用 clock.current_turn()——它应该在参数里拿到回合号

• 同理，decide 需要的随机性从参数传入的 rng_stream 取，而不是自己去调 rng.stream()

这带来的好处：

• 测试时可以手工构造任意回合号和随机子流，不需要启动整个系统

• 回放时更容易追踪：所有输入都在参数里，不需要猜测全局状态


——

4. 相位表调度范围限定（§2.4）

核心变化：相位表只能点名各层的公开相位入口（L2.resolve_phase、L3.resolve_phase），不能点名内部模块。

我的理解：

• 相位表里不会有 movement.execute 或 judge.assess 这样的条目

• 各层内部的调度由该层的 resolve_phase 负责

• 这保护了“跨层单一路径”原则——相位表不能绕过关卡直接调 L2 内部

确认：event_dispatch 相位调的是 checkpoint.translate——关卡翻译作为一个横切步骤，在相位表中占一个位置，但它不隶属于任何一层。这是合理的，因为关卡不属于 L2 也不属于 L3。


——

5. 拒收语义（§3.4）

核心变化：明确了命令在两种情况下失效的处理方式。

我的理解：

• 参谋翻译预检失败 → 生成“无法执行”事件，决断作废

• 引擎结算时前提消失 → 拒收该命令，生成 rejection 事件，回合继续

这个设计的关键点：

• 两种失败都走哨位落档，不静默丢弃

• orders 卷记录“曾想做什么”，events 卷记录“实际发生了什么”

• 开发期可配置中止回合（便于调试），但生产环境（活局）始终继续

这解决了上一版的一个隐含问题：如果命令被静默丢弃，复盘时会出现“我明明下了命令，为什么没执行”的困惑。现在意图和事实都有记录，可以对照分析。


——

6. 落成期检查单（§7.3）

核心变化：明确了几条 lint 级别的硬检查。

我的理解：

• 依赖方向检查：只准上层 import 下层（这是常规的）

• 类型隔离检查：L3 源码出现 Event 类型即失败（这是新的，且很重要）

• 子流白名单检查：rng 消费点必须在注册的子流内

• 档案权限检查：ledger 卷只能由 loop 写入

• 魔法数字检查：L2 代码中的裸数值即违例

其中第二条（类型隔离）是最有约束力的——它不是靠开发者的自觉，而是靠编译器/ linter 强制执行。这比任何文档规范都可靠。


——

一个开放问题

关于 world.apply(result) 的确认我想再明确一下：

结算函数的返回值是“增量补丁”还是“完整状态快照”？

• 如果是增量补丁：apply 负责合并，变更历史天然可追踪，但实现稍复杂

• 如果是完整状态快照：简单直接，但每次结算都要复制整个状态，可能有性能开销

我倾向于增量补丁，理由是：

1. 与事件流的哲学一致——事件本身就是增量描述

2. 方便 diff——可以精确知道这次结算改变了什么

3. 性能更好——不需要复制整个状态树

但如果选择增量补丁，需要明确定义补丁的格式和合并规则。

总体评价

v1.1 是一次高质量的修订。几个关键改进：

改进	解决的问题
世界状态显式化	L2 从无状态工具集变为有状态模拟器
关卡/哨位户主明确	横切职责集中化，避免分散在各层
纯函数接口规范化	测试性和确定性进一步提升
相位表范围限定	防止数据驱动被滥用为“开洞”借口
拒收语义明确	意图与事实分栏，复盘不留盲区
落成检查单	把设计原则转化为可执行的 lint 规则

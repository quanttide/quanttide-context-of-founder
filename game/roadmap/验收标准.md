验收系统路线图
定位先说清：这份路线图的交付物不是游戏本体，是那套“能证明游戏对了/好了”的工具链——一个 CLI 工具、一套断言集、一批金标准夹具、一份人类测试清单。它和游戏本体是两条并行线，但节奏咬合：本体每换一次真实现，验收系统先一步就位。
验收系统:  V0 ──→ V1 ──→ V2 ──→ V3 ──→ V4 ──→ V5
          夹具库   CLI骨架  回归+批量  断言全量  人类协议  常驻化
本体对应:  阶段0   阶段1   阶段2     阶段3    阶段4    阶段5
驱动层级:  —       L1      L1        L1       L2→L4    L1回归
V0：夹具库 + 金标准（与阶段 0 同步，约 1 周）
验收系统的地基是数据，不是代码。 在任何断言能跑之前，先手工造出一批“答案已知”的标准件：
1. 金种子集：固定种子的 RNG 流水，全项目共享一份；
2. 微型想定夹具：3–5 个手工构造的小想定——两个单位对撞、迂回包抄、隔河对峙、通信延迟场景——每个夹具手写期望结果（谁在哪回合接敌、战损区间、事件序列）；
3. 命令样例集：契约①②各一份合法/非法样本（非法样本用于校验器的负向测试）；
4. 验收 CLI 的第一个命令：hj validate——schema 校验器，只验格式不验内容。
通过标准：夹具和金标准过评审（“这个期望结果为什么对”能说清），validate 能拦住全部非法样本。
为什么先做这个：之后每个阶段的验收本质都是“真结果 vs 金标准”，金标准错了全盘皆错——它是整个验收系统的信用锚，值得在最便宜的时候人工打磨。
V1：CLI 骨架 + L1 自动断言（与阶段 1 同步，1–2 周）
交付 CLI 的最小驱动环：new / order / step / report / diff 五个子命令。
断言集第一版（纯 bash/脚本即可，不求框架）：
1. 闭环断言：脚手架脚本按 new→order→step→report 跑通一回合假桩闭环；
2. 确定性断言：同种子两次运行，hj diff 输出为空；
3. 契约断言：每回合进出文件过 validate；
4. 负向断言：喂非法命令文件，系统必须拒绝且报错可读（错误信息质量从这里开始验收）。
进 CI：这一版断言集直接挂提交钩子——以后本体每次提交自动全量重跑。
通过标准：换掉任一侧假桩，断言集不改动仍然全绿（验收系统第一次证明契约成立）。
V2：回归 + 批量（与阶段 2 同步，随真引擎 3–4 周渐增）
新增两个命令：hj truth（显式 —dev，默认关闭）、hj batch。
1. 夹具回归：V0 微型想定逐个跑，事件流与手写期望比对——真引擎第一版就对着“手工答案”调，而不是对着感觉调；
2. 分布基线：hj batch —seeds 1..100，产出 stats 首版——胜负比/战损/时长先记档不设卡（此时参数必然粗糙），建立“每次引擎改动后分布漂移可见”的机制；
3. 夹具扩容：真引擎会暴露 V0 想定覆盖不到的机制（撤退、溃散、补给），每实现一个机制补一个夹具——夹具数量是本阶段验收系统的核心 KPI。
通过标准：金种子集全绿进 CI；每个已实现机制至少有一个专用夹具；hj batch 稳定产出 stats。
V3：断言全量（与阶段 3 同步，2–3 周）
新增一个命令：hj intel（问参谋接口）。同时把断言集扩到迷雾和 AI：
1. 迷雾断言（自动化）：脚本比对 report 输出与 truth——不在场事件不可见、迟到报告的延迟符合通信排程、注入的假情报出现在账本且影响信念方向正确；
2. 可解释断言（自动化）：敌军 AI 每个决策必须携带依据（情报条目 ID + 性格权重），脚本可追溯无死角；
3. 性格扫描（半自动）：hj batch 扫谨慎度/冒进度参数，人工读结局分布是否合理——这是历史拟合的起点；
4. 对称性断言（自动化，防坑一的红线）：审查/测试确认敌军 AI 的输入输出与玩家路径完全一致——它读的也是投影，走的也是契约，truth 对它的决策记录零贡献。
通过标准：迷雾断言能抓住故意注入的三个泄密 bug（人工埋的）；AI 决策 100% 可追溯；对称性审查通过。
V4：人类验收协议（与阶段 4 同步，2 周）
验收系统在这里换挡：从自动化断言转向结构化的“人肉流程”，产出物是协议和记录表。
1. L2 协议（你本人 × CLI）：
• 一局完整对局，禁用 truth，只用 report/map/intel；
• 困惑清单：实时记录三样——表达不出的命令（语法缺陷）、误读的战报（投影缺陷）、失衡的节奏（设计缺陷）；
• 通过标准：能赢能输，每手说得出“我当时信了什么”。
2. L3 极简协议（新人 × 富文本）：一个未参与者只读战报打半局，复述测试——复述对了算过；
3. L4 准入清单：CLI↔界面对照表——界面上每条信息对应哪个 CLI 命令输出，逐条登记；这是 Flutter 接入的验收标准，也是防偷读真相的第二道锁；
4. 回归方式：每轮本体迭代后，L2 协议固定重跑一局（轻量版：10 回合）——困惑清单与 CI 断言同等对待。
通过标准：首次完整真人通关；困惑清单形成下一轮迭代的需求输入；对照表覆盖率 100%。
V5：常驻化（与阶段 5 同步及以后）
验收系统停止“扩张”，转入“值守”：
1. LLM 换装回归：战报润色/参谋对话接入 LLM 后，全量 L1 断言重跑——分布不应漂移（LLM 只碰文本层，漂移即违规，这条断言本身就是验收）；
2. 三件套日常化：hj batch（每次调参后）、hj diff（每次提交）、hj replay（每次 bug 定位）成为开发日常；
3. 验收系统自身的冻结原则：CLI 接口不再变更，新功能只加命令不改已有命令——和契约同一条纪律。
贯穿全程的纪律
1. 金标准人工把关：V0 之后的夹具可以脚本生成，但期望结果必须有人复核——验收系统的信用锚不容自动化污染；
2. 验收与本体同步交付：每个阶段本体的验收门禁，就是验收系统该阶段的全量断言绿——两条线不咬合即视为阶段未完成；
3. L2 不可省略：每阶段固定玩一局、记困惑清单，哪怕自动化全绿——这层产出的东西（语法/人感/节奏）没有任何断言能替代。
第一周动手清单（验收系统侧）：微型想定夹具 ×3 + 金种子 + hj validate——先让“答案”存在，再让“考试”成立。此后每个阶段的模式都一样：本体换真实现之前，验收系统先长出对应的能力等着它。

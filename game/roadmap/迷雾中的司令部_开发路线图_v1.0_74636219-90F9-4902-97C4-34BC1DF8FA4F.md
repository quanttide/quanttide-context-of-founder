# 《迷雾中的司令部》开发路线图

**版本**：v1.0
**日期**：2026-10-25
**上游文档**：《架构设计说明书 v1.1》《仓库现状盘点（quanttide/qtgame-war）》

> **修订说明**：本文件为排版规范化版本，内容与原路线图 v1.0 完全一致，仅统一标题层级、表格样式、代码块与速览视图，便于归档与评审。

---

## 0. 出发点：仓库现状与差距清单

本路线图的一切任务都锚定在仓库事实上，不做无来源的假设。

### 0.1 现有资产（可复用，不推倒）

| 资产 | 位置 | 对架构的意义 |
|------|------|--------------|
| 结算逻辑 | `src/studio/lib/models/combat.dart`、`game.dart`（`getMoveRange` / `getAttackTargets`） | L2 movement / combat 的现成领域知识，需重构签名后迁移 |
| 世界状态雏形 | `game.dart` 的 `GameState`（units 列表 + mapTerrain + currentTurn） | L2 world 的私有状态原型，但与结算逻辑同居一类，需分离 |
| 想定文件雏形 | `assets/campaigns/`（帝丘店战役 `campaign.json` / `map.json` / `units.json`） | v1.1 §2.2 想定概念的现实证据，援军波次（`ReinforcementWave`）是最有数据驱动味道的设计 |
| 相位意识 | `game_controller.dart` 的 `GamePhase` 枚举（player / ai / gameOver） | 有相位概念但硬编码在控制器，是 `phase_table` 的替换对象 |
| 领域知识 | `battlefield.dart`（六角格邻居、`hex_distance`） | L2 的几何知识，需明确归属避免塞进 movement |
| AI 玩法原型 | `docs/` 下 4 个 HTML 原型目录 + `spec/war.md` + PRD/ADD/QA | L3 概念已文档化，代码为零——设计先行、实现后到 |
| 事件雏形 | Dispatch 电报日志 | 是 UI 消息不是结构化事件流，可作 Event Schema 的素材 |
| 测试目录 | `tests/` | M1 起承接引擎包的确定性测试 |

### 0.2 四条核心差距（路线图要消除的对象）

| # | 差距 | 现状证据 | 由哪个里程碑消除 |
|---|------|----------|------------------|
| G1 | 引擎无独立身份：结算逻辑与 Flutter UI 同层同居，Dart 随机数裸用，无种子管理、无档案 | `models/` 与 `screens/views` 同目录混居 | M1 |
| G2 | 对局不可审计：无 Event/Report 区分、无关卡校验、无五卷档案、无 replay/diff | Dispatch 日志是唯一“事件”且非结构化 | M2 |
| G3 | 认知世界为零：fog/judge/decide/staff 只存在于 STATUS.md 与 spec 文档，代码零行 | `intel_view.dart` 是 UI 占位 | M3 |
| G4 | 人机与批量无分野：GamePhase 硬编码，无人类插头设计，无 batch、无 phase_table | `game_controller.dart` 单一控制器驱动一切 | M1（相位表）+ M3（autopilot）+ M4（人类插头） |

**两条超出架构书视野、需路线图反向吸收的仓库事实**：

1. README 承诺的两种玩法（互动剧本 / 兵棋推演上帝视角）对应 L4 的两个把手 → M4 处理；
2. 多维度后果（军事/消耗/政治三线）需在 M2 的事件 Schema 中预留槽位 → M4 填充。

### 0.3 周期与铁律

- **总周期估算**：单人业余投入（每周 10–15 小时），M1 约 4–5 周，M2 约 3–4 周，M3 约 6–8 周，M4 约 4–6 周，合计 **4–6 个月**。
- **M3 的 decide 纯函数是唯一预估困难段**——AI 的“感觉对不对”没有客观答案，设计迭代时间不可控，宁可高估。
- **贯穿规则**：前一里程碑验收未通过不进入下一个；每个 M 的“未达标处理”条款是路线图的一部分，不是备注。

## 1. M1 — 可复算（消除 G1）

> **目标**：引擎从 Flutter 应用中拆出，成为无 UI 依赖的纯 Dart 包；同种子双跑零偏离。

### 1.1 任务分解

#### T1.1 仓库结构与包拆分（1 周，对应 G1）

建立 Dart workspace + Melos 的 monorepo：

```
packages/
  engine/        ← 纯 Dart 包，pubspec 不出现 flutter，CI 强制检查
    lib/src/
      base/      clock.dart  roster.dart  rng.dart  ledger.dart
      engine/    params.dart  world.dart  kernel.dart
      phases/    movement.dart  combat.dart  supply.dart
      runtime/   phase_table.dart  loop.dart  checkpoint.dart
    engine.dart  （唯一公开入口）
  studio/        ← 原 src/studio 整体迁入，pubspec 增加 engine 依赖
  tools/         ← M2 的 CLI 把手住这里
```

迁移来源逐一对应：

| 原位置 | 目标位置 |
|--------|----------|
| `combat.dart` | `engine/src/phases/combat.dart` |
| `getMoveRange` / `getAttackTargets` | `engine/src/phases/movement.dart` |
| `GameState` 的 `units` + `mapTerrain` | `engine/src/engine/world.dart` |
| `battlefield.dart` 的邻居计算与 `hex_distance` | `engine/src/engine/world.dart` 的几何辅助（明确归属，不塞进 movement） |

`src/studio` 中被迁走的 `models/` 文件**删除，不留兼容垫片**——同一仓库无需过渡层。

#### T1.2 L1 四模块（1 周，对应“无确定性机制”）

| 模块 | 要点 |
|------|------|
| `clock` | 回合号唯一口径，从 `GameState.currentTurn` 中抽离，`advance()` 由 loop 独占 |
| `roster` | 番号注册表，以帝丘店 `units.json` 现有命名（`red3rdbattalion` 等）反推命名规则——不新造命名体系 |
| `rng` | 主种子一次性注入，按名字派生子流，消费点白名单未注册即抛错，**不提供 reset** |
| `ledger` | JSONL 追加读写器，接口只有 `append` / `read` / `size`；M1 先启用 `orders` / `events` 两卷 |

#### T1.3 kernel + world + 最小相位表（1.5 周，对应 G4 的相位部分）

- **kernel**：`resolve(action, context, rng_stream) → result`，纯函数，随机数只从传入子流取；
- **world**：私有状态持有者，`new_game(scenario)` 唯一初始化、`apply(result)` 唯一落账；M1 只支持单位位置、兵力、简单地形三要素；
- **相位表替换 `GamePhase` 枚举**：M1 五相位——

  ```
  friendly_decide → command_dispatch → movement_resolve → event_dispatch → archive_turn
  ```

  `friendly_decide` 暂由固定脚本命令驱动（真命令流 M4 接入）；`game_controller.dart` 的 `player/ai/gameOver` 分支逻辑随之退役；
- **loop**：关卡校验 + 哨位写入内置于相位之间。

#### T1.4 最小想定（0.5 周，对应仓库现有的想定雏形）

- `assets/campaigns/` 三个 JSON 升格为**想定 Schema v0**：地图拓扑、初始部署、主种子；
- `game.dart` 中硬编码的 `terrainProps` 全部迁入 `params`；
- 想定与 `params` 均写版本指纹；
- **帝丘店战役成为第一个通过校验的想定**。

#### T1.5 replay / diff 最小版（1 周）

- `tools/` 下新建 Dart CLI（`package:args`），暂不做完整命令族；
- `replay` 读档案重演；`diff` 逐事件对比并输出**第一偏离点的回合号、相位、两侧事件原文**；
- **不可省略**：M1 验收必须由 `diff` 机械判定，人肉肉眼不算数。

### 1.2 验收标准

| # | 标准 | 判定方式 |
|---|------|----------|
| A1 | `engine` 包无 Flutter 依赖 | CI 检查 pubspec |
| A2 | 同种子 + 同命令流，双跑 `events` 卷逐字节一致 | `diff` 报零偏离 |
| A3 | 改变主种子，`diff` 必现偏离并指出第一偏离点 | `diff` 工具 |
| A4 | 帝丘店想定 v0 加载通过校验、指纹落档 | CLI |
| A5 | Flutter 原型功能不回退（手动走一局） | 人工验收 |

### 1.3 风险与未达标处理

- **最大风险：浮点非确定性**——Dart 的 `double` 跨平台不保证一致。
  **对策**：`engine` 包禁用 `double`，数值用整数（米、厘、万分比），进 lint 检查。这条从 M1 第一天执行，M3 之后补成本极高。
- **未达标处理**：A2/A3 不过即冻结新功能，只做确定性修复直至通过；**禁止以“临时容忍差异”换进度**——确定性破了，后续所有里程碑地基都是假的。

## 2. M2 — 可复盘（消除 G2）

> **目标**：五卷案卷齐备、关卡翻译焊死、把手层五件套可用，帝丘店战役完成第一次完整对局与完整对质。
> **前置**：M1 验收通过。

### 2.1 任务分解

#### T2.1 combat / supply 模块化（1.5 周）

- **combat**：`combat.dart` 重构为 `execute(world, order_a, order_b, turn)` 签名，随机数走子流；
- **supply**：新建（仓库现有代码中无对应物，`spec/war.md` 有设计）。帝丘店先做最简模型：补给线连通性判定 + 补给状态事件，复杂规则延后——supply 是“看不见的系统”典型，M2 先给可断言的最小形态，M4 加深度；
- 两模块数值全部进 `params`，消灭残余魔法数字。

#### T2.2 相位表补齐（0.5 周）

扩展至 v1.1 §2.4.2 完整十相位（含 `combat_resolve`、`supply_evaluate`、`enemy_*` 占位）；相位表指纹落档。

#### T2.3 关卡与登记哨完整化（1 周，对应 G2 的核心）

- **checkpoint**：Event → Report 翻译实现，翻译函数落在 `engine/src/runtime/checkpoint.dart`；M2 阶段 L3 未存在，M3 建包时迁移为 L3 的唯一输入；
- **Event Schema** 以现有 Dispatch 电报日志为素材起步：`type`、`unit_id`、`turn`、`phase`、`consequences` 预留槽位；
- **lint 立规**：`engine` 包内禁止 Event 类型跨 `runtime` 边界导出；M3 建 L3 时升格为“L3 源码出现 Event 即编译失败”；
- `intel` 卷从 M2 起记录（M1 只有 `orders` / `events` 两卷）。

#### T2.4 想定文件完整化（1 周）

- 帝丘店想定升格：援军波次（`ReinforcementWave`）正式进 Schema——现有 `campaign.json` 里最有价值的设计，保留并升格，不重造；胜负判定条件进 Schema；
- 多维度后果在事件 Schema 预留 `consequences` 槽位——M2 不实现三线结算，但结构留位，M4 填充，避免届时改档结构。

#### T2.5 把手层五件套（1 周）

- CLI 命令族成型：`hj new` / `step` / `report` / `truth` / `validate` / `diff` / `replay` / `inspect`；
- `inspect` 先支持翻 `orders` / `events` 两卷（`decisions` 卷 M3 才有内容）；
- `diff` 增强：支持对比任意两份档案的任意两卷。

### 2.2 验收标准

| # | 标准 | 判定方式 |
|---|------|----------|
| A1 | 帝丘店全流程（脚本命令驱动）跑完，五卷齐备且通过 `validate` | CLI + `validate` |
| A2 | 同种子重跑，`diff` 零偏离（含 `intel` 卷） | `diff` 工具 |
| A3 | 故意注入一处结算偏移，`diff` 在 3 分钟内定位第一偏离回合与相位 | 人为注错演练 |
| A4 | 援军波次与胜负条件从想定数据读取，改 JSON 改结局、代码零改动 | 改档验证 |
| A5 | 事件 Schema 含 `consequences` 预留槽位 | Schema 审查 |

### 2.3 风险与未达标处理

- **最大风险：combat 重构引入行为漂移**——原 Flutter 原型已有隐性玩法平衡，纯函数化时数值口径易变。
  **对策**：迁移前先在旧代码上录制一组“旧结局基线”（输入命令 + 输出战损序列），重构后 `diff` 对基线，漂移要么解释、要么修复。
- **未达标处理**：A3 注错演练失败说明 `diff` 粒度不够，**先补 `diff` 再继续**。

## 3. M3 — 可对弈（消除 G3）

> **目标**：L3 敌军侧四纯函数全部落地，batch 双 AI 对弈可用；帝丘店战役出现第一场“AI 对 AI”的完整战役。
> **前置**：M2 验收通过。

### 3.1 任务分解

#### T3.1 L3 包建立与类型焊死（0.5 周）

- 新建 `packages/command/`（L3 司令部包，纯 Dart，依赖 `engine` 的 Report 类型与 `params`）；
- `checkpoint` 的 Event → Report 翻译函数从 `engine/src/runtime` 迁至 `command` 包唯一入口；
- **lint 升格为硬检查**：`command` 包源码出现 Event 类型即编译失败——迷雾从这一刻起焊死在类型层。

#### T3.2 fog 认知管线（1 周）

- 过滤、延迟、失真三道处理，失真参数进 `params`；
- 帝丘店战役的情报规则（`spec/war.md` 已有设计）作为首个参数化实例；
- 验收素材：`docs/` 下情报意图 HTML 原型的行为描述作为 fog 的手写期望时间线。

#### T3.3 judge 研判（1.5 周）

- `assess(turn, reports[], beliefs_old) → beliefs_new`，纯函数，回合号显式传参；
- 先实现最简形态：位置估计 + 置信度，不做复杂推断；
- **可断言性质先写清单再写代码**（沿用启发式卡方法）：如“同一情报两次重算的估计跳变不超过 X”。

#### T3.4 decide 决断（2–3 周，全路线图最大的不确定项）

- `decide(turn, beliefs, rng_stream) → decision`，候选行动打分 → 择一；
- **权重与候选集全部进 `params`**——为 M4 的参数扫描铺路，M3 就要把参数化做彻底；
- 决策日志：`decide` 的每次输出落 `decisions` 卷（`loop` 写入，`decide` 保持纯函数）；
- **验收方式**：不用“AI 打得好”这类主观标准，用结构断言——信念置信度低时不应全力进攻、候选打分与最终选择一致等性质断言集全部通过；“感觉对不对”留给 M4 的人工对局审。

#### T3.5 staff 参谋翻译器（1 周）

两级展开：战术展开 → 逐条合法性预检；非法命令生成事件回报而非静默丢弃（对应 v1.1 §3.4 拒收语义）。

#### T3.6 batch 与双 AI 对弈（0.5 周）

- `loop` 的无人值守模式：双 autopilot 喂种子出档案，与人机共用同一张相位表（v1.1 的 `friendly_decide` 相位在 batch 下无人类输入即自然走 autopilot）；
- 参数扫描 CLI（`hj sweep`）：M3 就提供最简版，为 M4 调参积累工具。

### 3.2 验收标准

| # | 标准 | 判定方式 |
|---|------|----------|
| A1 | `command` 包源码零 Event 引用（lint 通过） | CI |
| A2 | 双 AI 对弈帝丘店战役全程跑完，五卷档案齐备 | `batch` CLI |
| A3 | `decide` 的性质断言集全部通过 | 测试套件 |
| A4 | 同种子 batch 双跑 `diff` 零偏离 | `diff` 工具 |
| A5 | 一次参数扫描（如 `fog.distortion` × 5 值 × 10 种子）产出曲线表 | `sweep` CLI |

### 3.3 风险与未达标处理

- **最大风险：decide 的“感觉不对”无客观判据，迭代可能拖垮工期。**
  **对策**：性质断言集先于实现写好，断言过了就算 M3 达标——“好不好的唯一来源是人工对局审”（v1.1 已明确），M3 不背这个锅。
- **次要风险**：AI 行为使战役早早失衡（如某方必胜），导致 batch 产物单一。
  **对策**：先调 `decide` 参数边界而非代码；参数扫描暴露的陡峭区记入 M4 待办。
- **未达标处理**：A3 不过即冻结 M4——**AI 不可解释则人类插头接上也没有意义**。

## 4. M4 — 可交付（消除 G4 收尾，完成两种玩法承诺）

> **目标**：人类命令插头接入、dev 仪表盘上线、参数扫描驱动调参、多维度后果落地，帝丘店战役达到可给真人玩的状态。
> **前置**：M3 验收通过。

### 4.1 任务分解

#### T4.1 人类命令插头（1 周）

- `friendly_decide` 相位接受人类输入覆盖 AI，输入格式与 autopilot 决断输出完全一致（v1.1 §3.3）；
- CLI 对局入口：`hj play` 提供命令式人机对局；
- Flutter 端接回：`src/studio`（现 `packages/studio`）从“直接调 Game 内部方法”改为“只调 engine 公开入口与 CLI 输出”——清除 UI 与引擎同居的最后残留；
- **兵棋推演模式（上帝视角直接点棋子）作为 L4 的第二个把手接入**：它绕过 L3 直达 L2，是 README 双玩法承诺的另一半，由仓库 README 倒逼出的需求，路线图在此显式承接。

#### T4.2 dev 仪表盘四件套（1.5 周）

| 仪表 | 数据源 | 铁律 |
|------|--------|------|
| 信念轨迹图 | 真相读 `events` 卷、信念读 `beliefs` 卷 | 不做活体查询，只读档案 |
| 通信时间线 | `intel` 卷 | — |
| 决策追踪器 | `decisions` 卷 | — |
| 战损直方图 | batch 产物 | — |

优先在 CLI/终端以文本 + 简图形态交付，Flutter 可视化视剩余时间决定——先用最糙手段验证这些图真的被使用。

#### T4.3 参数扫描驱动调参（1.5 周）

- 扩展 M3 的 `sweep`：失真率、谨慎度权重、信念重算周期的系统扫描；
- 扫描结果存档、跨版本对比（曲线漂移方向可见）；
- **每周一次“重演金标准对局 + 重扫参数”的固定节奏在此建立**。

#### T4.4 多维度后果落地（1 周）

- 三线（军事/消耗/政治）结算填充 M2 预留的 `consequences` 槽位；
- 帝丘店战役的三线数值进入 `params`，想定文件更新。

#### T4.5 supply 深化（1 周）

- 从 M2 的连通性判定升级为有深度的补给模型（`spec/war.md` 的完整设计）；
- supply 的参数敏感性扫描纳入 T4.3 的例行节奏。

#### T4.6 文档与验收对齐（0.5 周）

### 4.3 风险与未达标处理

- **最大风险：范围蔓延**——M4 是最容易“再润一下”的里程碑。

- **次要风险**：仪表盘的 UI 打磨时间失控。
  **对策**：文本形态先验收，可视化是可选加分项而非验收标准。

## 5. 跨里程碑的固定纪律

| 纪律 | 内容 |

| **确定性测试常青** | M1 建立的“同种子双跑零偏离”测试在每个里程碑结束、每次引擎改动后必跑，红了即回滚 |
